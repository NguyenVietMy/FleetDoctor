# Ticket15 chaos campaign

Ticket15 is implemented as a fail-closed controller in `scripts/chaos_campaign.py`. It adapts the existing disk, inode, FD, OOM, CPU, network, DNS and I/O validators; it does not replace scenario evidence with a generic success flag. Local fixtures are synthetic and can never establish AWS acceptance.

## Frozen inputs

The version 2 manifest binds both the approved correction plan and archived original plan; the reviewed baseline and every inspected source byte; Ticket14 evidence; installed controller, wrapper, helper, protected-manifest and canonical controller-bundle hashes; effective configuration; exact lab facts; deterministic OOM leaves; role-specific monitor/node cgroups and node PID selectors; cadence/deadlines; assignments; and the connection, preparation and runtime receipt hashes.

Baseline is historical review provenance. It is separate from the actual source revision and full byte hashes, which may be dirty before publication or a later clean commit after publication.

The operator-generated connection receipt must be no more than ten minutes old when authorizing new work. For each role it binds the current SSH IP:22 separately from the attested private collector identity, a plain ED25519 host key/fingerprint, normalized inventory and host-key provenance hashes, boot ID, protected manifest and controller bundle. SSH uses a private one-host pin file, `-F none`, ED25519-only strict checking, no connection sharing or user/global host database mutation. A nonce hello authenticates a fresh session and binds batch, role, instance, private IP, boot, host key, protected manifest and bundle before any mutation. Random nonce/session values may differ across prepare, preflight, run and cleanup; stable attestation fields must not. A historical receipt may authorize only exact receipt-bound cleanup after its freshness window, and future-dated or identity/provenance-different receipts are always rejected.

The live runtime receipt is captured after selector preparation. It binds the connection and preparation receipts, source, installed bytes, effective configuration, lab facts, normalized provenance and the stable hello attestations. Preflight re-hashes the checkout and reads `/health`, `/configuration` and node metrics only through the verified monitor session to `http://<attested-monitor-private-ip>:8000`. There is no production API URL, tunnel, token-file or host override. The relay permits bounded read-only campaign routes, ignores proxy environment, rejects redirects and applies one total wall-clock deadline to connect, headers and body. Every attempt boundary compares node metric boot IDs with both verified node sessions.

## Ownership and recovery

Only `/usr/local/sbin/fleetdoctor-chaos-controller` may be invoked remotely. The installed wrapper is copied from the LF-pinned `deploy/fleetdoctor-chaos-controller.sh` and executes the fixed `/usr/bin/python3.11` with protected `/opt/fleetdoctor/current/deploy/chaos_controller.py`; no caller `PATH`, environment-selected interpreter or writable source path selects privileged code. The wrapper, controller and every helper hash must match `/etc/fleetdoctor/chaos-controller.json`. Startup verifies the source/deploy directories and every executable source object as root-owned, regular, non-symlink and not group/world writable. `deploy/install-chaos-controller.sh` verifies those properties before importing the validator, installs only the wrapper, manifest and owned controller-state directories, and does not rewrite unrelated source-directory metadata.

The authenticated newline JSON protocol has fixed role/scenario/action/argument allowlists, 64 KiB helper bounds, a separate 512 KiB API envelope, bounded helper output and 150-second helper deadlines. Node sessions retain the 4,096-request limit. The monitor permits 200,000 requests; the documented worst case is 131,600 reads (`12 * 45 * 240 + 2000`). All sessions remain finite at six hours with terminal cleanup reserve.

Configuration ownership is separate from the single physical fault/resource owner. Up to eight configuration transactions are tracked in order. EOF/signal/failure performs conclusive terminal fault teardown first, including OOM stop/release or I/O workload cleanup/mapping destruction, then restores configurations in reverse order with their exact monitor/agent scope. FD release and I/O workload cleanup are deliberately nonterminal. Foreign-token mutating actions and inconclusive cleanup replies retain ownership and fail closed.

A Linux `flock` permits one persistent controller per node and is kernel-released on crash. The campaign machine uses a common lease keyed only by account/region/AZ and role-to-instance IDs. Batch ID, output path, kernel, IP, state and CPU-credit changes cannot bypass it. `recover` removes it only for the exact stable lab when PID plus creation identity is no longer live. Windows liveness uses a read-only process query and never signals a process.

`deploy/config_transaction.py inventory` returns only parsed selector sets, missing keys, environment hash, metadata and service state—never unrelated values or rollback bytes. It supports the generated single-line quoted/unquoted syntax and CRLF/non-UTF8 unrelated bytes, while duplicate, multiline or ambiguous assignments fail closed. Preparation inventories monitor, node-a and node-b before the first write, requires exact manifest equality, preserves each actual set, and sends the exact hash/selector before-state to `begin`. `begin` re-reads immediately, refuses stale state or a dropped member, and only then writes. FD repeats that check before worker creation and immediately before adding its exact PID. Exact-byte/metadata/service restoration and reverse rollback remain unchanged.

## Measurements

New controller sessions refuse malformed, oversized or unresolved prior journals and release their newly acquired lease on rejection. Retention is bounded to128 session journals of at most16MiB each; archive completed evidence privately before that limit, preserving its hashes. Unconfirmed terminal cleanup returns an error, and the client allows the declared30-minute teardown reserve rather than killing a valid cleanup after30seconds. An unresolved root journal remains HOLD for an owner-reviewed, resource-specific repair; the client never clears it automatically. Before a trusted operator archives that journal, retain its original bytes/hash, prove exact-token resource cleanup and reverse configuration restoration, and verify healthy observations. PID death or elapsed time alone is insufficient. Cleanup-purpose sessions are locally restricted to read-only inventory plus exact-token lookup/status/adopt/restore for their receipt-bound role and scope; they cannot start a campaign, inject a fault, begin a transaction or touch a different token. `lookup` returns only that token's validated active state or exact absence. `recover` opens and authenticates every role before mutation, then restores only the exact manifest-owned monitor and agent transactions in reverse order; an already absent exact token is idempotent success. Direct protected configuration recovery remains a separate operator repair tool.

Every attempt records injection start, first validated ordinary resource trigger, first matching new incident response completion, cleanup and automatic resolution on one controller monotonic clock. Detection and recovery each have a hard 60-second response-completion deadline.

CPU requires initialized target/reference telemetry, exact coverage, fresh busy/runnable trigger, new incident ID, exact node/rule/resource/configuration/severity/opening identity, immutable opening evidence, reference continuity and distinct continuous healthy recovery samples.

OOM reuses `workload`, `generation_key` and `add_recovery_sample`. Resource is `cgroup|boot_id|st_dev|st_ino`, never the cgroup display path alone. Its manifest leaf is exactly `/system.slice/fleetdoctor-oom-<attempt-token>.service/workload`. It requires continuous empty stable baselines of that generation, matching helper generation, finite 48 MiB/zero-swap limits, separated monitors, current local `oom_kill`, exact opening/latest evidence and investigation steps, kernel-kill plus allocator-death helper proof before stop, current recovery counters, all-incident target/reference exclusion and final owned release.

CPU uses three fresh continuous low target/reference baselines, accepts a valid high ordinary trigger even when the expected incident appears in the same poll, and binds post-injection/post-cleanup identities, complete opening/latest evidence, investigation steps and all-incident exclusion. The other six adapters preserve their scenario-specific safety, identity, evidence, reference and recovery validators. I/O prepares distinct token-bound mappings on both target and reference controllers; workload stop, recovery and final mapping destruction remain separate. Network runs latency then loss with full recovery between. Aggregation requires exactly 40 unique attempts, exact phase names/tokens/references, common identities, unique incidents, helper/API event-linked raw evidence, cleanup and automatic recovery. Injection, trigger, diagnosis, cleanup and recovery times plus UTC correlations are validated and both durations recomputed. Every scenario median must be strictly below 30 seconds; network also gates both profile medians and the median of each run's slower phase. Calibration is a separate 16-trial manifest.

## Commands

Calibration declares two deterministic OOM leaves, one per assigned node trial. The measured batch declares five. Each batch has its own preparation, runtime receipt and frozen manifest.

All outputs, locks, manifests and receipts stay outside the checkout at new paths.

uv run python scripts/chaos_campaign.py validate --manifest C:/private/ticket15/measured-manifest.json --connection-receipt C:/private/ticket15/connections.json

uv run python scripts/chaos_campaign.py preflight --manifest C:/private/ticket15/measured-manifest.json --connection-receipt C:/private/ticket15/connections.json --key C:/private/fleetdoctor-key --checkout C:/Users/VietM/.fleetdoctor/task15-20261111-claudex/worktree --runtime-receipt C:/private/ticket15/live-runtime.json --output C:/private/ticket15/preflight.json

The controller manifest is schema2 and binds role, batch, both plan hashes, stable account/region/AZ/instance/private identity, controller/wrapper/helper hashes and canonical bundle digest. Generate independently verified inventory and host-key artifacts, normalize and hash their fields into `connections.json`, then install only frozen bytes. `prepare-runtime` opens and authenticates all roles before its first write. `run` never begins the outer transaction. Example paths are documentation-only; actual endpoints come only from the receipt.

## Live work order

After separate authorization: verify the exact account and three existing instance IDs; preserve initial state; deploy only frozen inspected bytes; install and validate the protected controller manifest/wrapper on all three hosts. Prepare the separate calibration batch, capture its preparation/runtime receipts, freeze its manifest, run its 16 trials, export the results and restore its exact outer configuration. Only after calibration succeeds, prepare the measured batch with its five new OOM leaves, verify installed hashes/effective configuration, capture fresh preparation/runtime receipts and freeze the measured manifest. Execute its preflight and uninterrupted 40-run batch, export and aggregate, then restore the exact receipt-bound outer configuration, exact service states and approved instance state. Retain actual billing separately. Never reuse calibration receipts as measured runtime evidence. Any source/rule/configuration change requires new proof, inspection, deployment, receipt and freeze.

This repository contains no AWS campaign result. Native/service proof, publication CI, live campaign, billing, fresh independent inspection and owner acceptance remain separate gates.
